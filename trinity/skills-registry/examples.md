# Orchestration Examples

Concrete end-to-end examples showing how the Product Trio skill orchestrates sub-skills in practice. These examples demonstrate phase detection, skill selection, parallel execution, and output integration.

---

## Example 1: Simple Discovery → Recommendation

**User:** "Should we add user-generated tags to Capterra product pages?"

### Phase Detection
- Contains: "should we" → Discovery mode
- Load: `discovery-phase.md`, `brands/capterra.md`, `lenses/buyer-experience.md`

### Trio Analysis

**POV Designer:**
Tags can improve findability BUT risk cluttering the scan-first layout. Need clear visual hierarchy. Also: who moderates tags? Bad tags (spam, off-topic) hurt trust.

**POV Developer:**
Tag infrastructure is non-trivial—storage, search indexing, moderation queue, spam prevention. Also affects page load (more DB queries). SEO impact unclear (user-generated content signals).

**POV Product Manager:**
Opportunity: Better product discovery. Risk: Tag quality varies, moderation cost unknown. **Invoke `competitive-analysis` to understand how others handle this.**

### Skill Orchestration

```
Invoke: competitive-analysis
Scope: "Check how G2, TrustRadius, and Gartner Peer Insights handle 
       user-generated tags on product pages. Focus on: tag quality, 
       moderation, spam prevention, SEO impact."
```

### After Skill Completes

**Competitive Analysis found:**
- G2: Uses tags, but moderates heavily (30% rejected); SEO neutral
- TrustRadius: No user tags (editorial only); cited moderation cost
- Gartner: Uses tags in restricted form (predefined list, not free-form)

**Updated Trio Analysis:**

**Disagreement:**
- Designer: "Free-form tags will be messy; predefined list maintains quality"
- Developer: "Predefined list is easier to implement and maintain"
- PM: "Free-form unlocks more discovery value, but moderation cost is 3x"

**Recommendation:**
Start with predefined tag list (50 common tags across top 20 categories). Test with buyers: Does it improve product discovery? If yes and buyers request more tags, expand carefully with moderation.

**Why:** If moderation cost exceeds 1 FTE OR tag quality drops below 80% useful, revert to editorial-only.

**Validation:**
- A/B test on 100 mid-traffic product pages
- Measure: Click-through from tags, tag usage rate, moderation queue size
- Duration: 4 weeks
- Decision: If tag CTR >5% AND moderation <10 hrs/week → expand to 500 pages

## Example 2: Design + Implementation in Parallel

**User:** "Build the AI category summary feature for Capterra that we discussed"

### Phase Detection
- Contains: "build" → Implementation
- Implicit: Needs design first → Design
- Load: `design-phase.md`, `implementation-phase.md`, `brands/capterra.md`, `lenses/buyer-experience.md`

### Trio Analysis

**POV Designer:**
UI needs: Summary block at top of category page, citation links to products mentioned, "Generated by AI" trust label, mobile-first (most traffic), fast-scan optimized.

**POV Developer:**
Architecture: Batch generation (not per-pageview), 24h TTL cache, eval harness with 95%+ accuracy, fallback to no-summary for edge cases (new/small categories). Cost: ~$2.50/category/month at scale.

**POV Product Manager:**
Goal: Reduce time-to-first-product-click by 10%+. Validation: A/B test on 50 mid-sized categories for 2 weeks. Track: time-to-click, PPC CTR, bounce rate.

**Disagreement:**
- Designer: "Make summary skimmable (bullets, not prose)" vs Developer: "Prose is easier to generate reliably"
- All agree: Citations are non-negotiable (trust signal)

**Recommendation:**
Build with: Bullet-format summaries (Designer wins on UX), batch generation with 24h cache (Developer approach), A/B test plan (PM validation). Proceed with implementation.

### Skill Orchestration

**Spawn in parallel (same turn):**

```
Agent 1: Invoke `web-prototype-taste-brutalist`
  Task: "Build Capterra category summary UI component:
    - Bullet-format summary (3-5 bullets)
    - Citation links to mentioned products
    - 'Generated by AI' label with info icon
    - Mobile-first, responsive
    - Scan-optimized layout (doesn't block product listings)"

Agent 2: Invoke `tdd-workflow`
  Task: "Implement AI category summary backend:
    - Batch generation job (runs nightly)
    - 24h TTL cache in Redis
    - Eval harness (95%+ accuracy threshold)
    - Fallback to no-summary for <30 reviews
    - API endpoint: GET /categories/:id/summary
    - Test coverage: generation logic, caching, fallbacks"

Agent 3: Invoke `competitive-analysis` (in parallel for context)
  Task: "Quick scan: How do top 3 competitors (G2, TrustRadius, 
         Software Advice) position AI-generated content? Any trust 
         signals we're missing?"
```

### After Skills Complete

**Agent 1 (Frontend):** React component ready, mobile-responsive, trust signals present
**Agent 2 (Backend):** API implemented, tests passing (94% coverage), batch job ready
**Agent 3 (Competitive):** All use citation links + human review; we're aligned

**Updated Trio Validates:**

**POV Designer:** "UI matches spec—scan-friendly, trust signals clear, mobile works well"

**POV Developer:** "Implementation solid—batch generation scales, fallbacks tested, cost model validated ($2,250-5,000/month for all categories)"

**POV Product Manager:** "Ready for validation. Deploy to staging, run A/B test on 50 categories."

**Output:**
```
Implementation complete:
- Frontend: /components/CategorySummary.tsx
- Backend: /api/categories/summary.ts + batch job
- Tests: 94% coverage, all passing
- Staging: Deployed, ready for A/B test

Next steps:
1. Enable feature flag for 50 mid-sized categories (A/B test)
2. Run for 2 weeks, monitor metrics:
   - Time-to-first-product-click (target: ↓10%+)
   - PPC CTR (target: hold or increase)
   - Bounce rate (target: hold or decrease)
3. Decision rule: If targets met → expand to 200 categories
```

## Example 3: Parallel Disagreement Exploration

**User:** "We're divided on how to improve Software Advice's advisor matching. Designer wants user research, Developer wants to prototype and test, PM wants competitive analysis. Help us decide."

### Phase Detection
- Explicit disagreement with multiple approaches → Parallel exploration mode
- Load: `discovery-phase.md`, `design-phase.md`, `brands/software-advice.md`

### Trio Analysis

**Disagreement (explicit from user):**
- Designer: "Ethnographic research—shadow 10 buyers + 5 advisors, understand real workflow" (Slow, deep)
- Developer: "Build instrumented prototype, deploy to staging, watch real behavior" (Fast, empirical)
- PM: "Competitive analysis + user interviews—what works elsewhere + what buyers want" (Balanced)

**Recommendation:** 
All three approaches have merit. Run them **in parallel** for 1 week, synthesize findings, make informed decision.

### Skill Orchestration

**Spawn 3 agents in parallel:**

```
Agent 1: Invoke `deep-research`
  Task: "Ethnographic research on Software Advice advisor matching:
    - Shadow 10 buyer sessions (watch advisor calls, observe decision-making)
    - Interview 5 advisors (what info do they need to match well?)
    - Document: Pain points, information gaps, decision criteria
    - Time-box: 1 week
    - Output: Research report with key findings + recommendations"

Agent 2: Invoke `web-prototype` + instrumentation
  Task: "Build instrumented prototype of improved advisor matching:
    - 3 matching algorithm variants (rule-based, ML-based, hybrid)
    - Deploy to staging with advisor team
    - Instrument: Which variant leads to better lead quality?
    - Measure: Match time, advisor confidence, lead conversion rate
    - Time-box: 1 week
    - Output: Prototype + metrics on which variant performs best"

Agent 3: Invoke `competitive-analysis` + user interviews
  Task: "Competitive + user research on advisor matching:
    - Competitive: How do 3 competitors handle advisor-buyer matching?
    - User interviews: 10 buyers who used Software Advice—what made 
      a good/bad match?
    - Time-box: 1 week
    - Output: Competitive patterns + buyer needs synthesis"
```

### After All Agents Complete (1 week later)

**Agent 1 (Ethnographic Research) found:**
- Advisors need buyer's "maturity stage" (just exploring vs ready to buy now)
- Buyers frustrated when advisors don't understand their industry specifics
- Time spent on call: 15-30 min; advisors want pre-call context to shorten this

**Agent 2 (Prototype) found:**
- Hybrid algorithm (rules + ML) performed best: 85% advisor confidence vs 70% rule-based
- ML-only was black-box; advisors didn't trust it
- Key signal: Buyer's industry + urgency + budget predict best match

**Agent 3 (Competitive + User Interviews) found:**
- Competitors use pre-qualification forms (capture industry, urgency, budget)
- Buyers willing to fill 5-7 fields if it means better match
- Best practice: Show matched advisor's expertise upfront (trust signal)

**Synthesize Findings:**

**POV Designer (informed by Agent 1):**
"Research confirms: Buyers need to see advisor expertise upfront. Pre-call form should capture industry + urgency. Make form feel like progress, not a gate."

**POV Developer (informed by Agent 2):**
"Hybrid algorithm wins—combine rules (industry match) with ML (behavior prediction). Advisors trust explainable matches. Build with rule-based MVP, layer in ML later."

**POV Product Manager (informed by Agent 3):**
"Competitive pattern: Pre-qualification form is standard. Our edge: Show matched advisor's industry expertise immediately after form fill (trust + commitment)."

**Disagreement (resolved by parallel exploration):**
All three approaches uncovered the same root cause: **Matching needs more buyer context upfront**. The solution emerged from synthesizing all three approaches, not choosing one.

**Recommendation:**
Build two-step matching flow:
1. Pre-qualification form (5 fields: industry, urgency, budget, team size, current tools)
2. Instant advisor match with expertise display ("Sarah specializes in HR software for 50-200 person healthcare teams")

Hybrid matching algorithm (rules + ML). Start with rule-based MVP, add ML prediction layer in Q4.

**Validation:**
- A/B test with 20% of traffic for 3 weeks
- Metrics: Form completion rate, advisor confidence score, lead-to-sale conversion
- Decision: If conversion ↑10%+ AND advisor confidence ↑15% → roll out to 100%

**Output:**
```
Parallel exploration complete. All three POVs converged on same insight:
- Need: More buyer context upfront
- Solution: Pre-qualification form + expertise-matched advisor
- Algorithm: Hybrid (rules + ML)

Next: Implement the two-step flow
```

## Example 4: Sequential Discovery → Design → Implementation → Validation

**User:** "Help me build a vendor dashboard widget showing review response rate for GetApp"

### Phase 1: Discovery

**Phase Detection:** "vendor dashboard" + "GetApp" → Vendor Experience
**Load:** `discovery-phase.md`, `brands/getapp.md`, `lenses/vendor-experience.md`

**Trio Analysis:**

**POV Product Manager:** "Before designing, let's understand what vendors actually want to know about review responses. **Invoke `deep-research` on vendor needs.**"

**Skill Orchestration:**
```
Invoke: deep-research
Task: "Research vendor needs for review response metrics:
  - What do vendors want to know? (just response rate, or also time-to-response, sentiment, effectiveness?)
  - Competitive: What do G2, Capterra, TrustRadius show in their dashboards?
  - Internal data: Check support tickets—what review-related questions do vendors ask?
  - Output: Requirements for the widget"
```

**Research found:**
- Vendors want: Response rate, avg time-to-response, reviewer re-engagement rate
- G2 shows: Response rate + "responses that led to profile updates"
- Support tickets: "How quickly should I respond?" and "Do responses help my ranking?"

**Trio updates recommendation:**
"Widget should show: Response rate (%), avg time-to-response (days), and impact on profile views. Now let's design it."

### Phase 2: Design

**Phase Detection:** Discovery complete → Design phase
**Load:** `design-phase.md`

**POV Designer:** "Dashboard widget for vendor dashboard—data-dense, professional, GetApp brand. **Invoke `dashboard` skill for data visualization.**"

**Skill Orchestration:**
```
Invoke: dashboard
Task: "Design review response rate widget for GetApp vendor dashboard:
  - Metrics: Response rate (%), avg time-to-response (days), profile view impact
  - Visual: Simple chart (line graph for trend, big number for current rate)
  - Benchmark: Show industry average for comparison
  - CTA: 'Respond to pending reviews' button
  - Brand: GetApp (professional, tech-forward, data-rich)"
```

**Design complete:** Dashboard widget mockup with charts, metrics, and CTA

### Phase 3: Implementation

**Phase Detection:** Design approved → Implementation phase
**Load:** `implementation-phase.md`

**POV Developer:** "Implement with tests—this is vendor-facing and data-driven. **Invoke `tdd-workflow`.**"

**Skill Orchestration:**
```
Invoke: tdd-workflow
Task: "Implement review response rate widget for GetApp vendor dashboard:
  - Frontend: React component matching dashboard design
  - Backend: API endpoint GET /vendors/:id/review-response-metrics
    - Calculate: response_rate, avg_time_to_response, profile_view_impact
    - Benchmark against industry average
  - Tests: Widget rendering, API endpoint, metric calculations
  - Cache: 1-hour TTL (data doesn't need real-time)
  - Error handling: Graceful degradation if metrics unavailable"
```

**Implementation complete:** Code ready, tests passing (92% coverage)

### Phase 4: Validation

**Phase Detection:** Implementation done → Validation phase
**Load:** `validation-phase.md`

**POV Product Manager:** "Validate that vendors find this useful and it drives engagement. **Measure adoption and behavior.**"

**Skill Orchestration:**
```
Invoke: performance-analysis
Task: "Measure dashboard widget performance:
  - Load time: Ensure widget renders <500ms
  - API latency: Check metrics endpoint response time
  - Dashboard overall: Ensure widget doesn't slow down other widgets"

A/B test plan (inline, no dedicated skill available):
- Enable for 50% of GetApp vendors with pending reviews
- Measure: Widget engagement rate, 'Respond to reviews' CTA clicks, review response rate change
- Duration: 2 weeks
- Decision: If CTA clicks >15% AND response rate ↑10% → roll out to 100%
```

**Performance results:** Load time 320ms, API latency 180ms, no impact on other widgets

**A/B test results (after 2 weeks):**
- Widget engagement: 42% of vendors clicked in
- CTA clicks: 18% clicked "Respond to pending reviews"
- Review response rate: ↑14% vs control group

**Trio validates:**

**POV Designer:** "Engagement is strong—vendors are using it. Consider adding tooltips for 'profile view impact' (some confusion in support tickets)."

**POV Developer:** "Performance is solid, no issues reported. Add tooltip text in next sprint."

**POV Product Manager:** "Clear win: ↑14% response rate means better vendor engagement with buyers. Ship to 100%, add tooltip improvement to backlog."

**Output:**
```
Review response rate widget: SHIPPED to 100% of GetApp vendors

Results:
- Widget engagement: 42%
- CTA clicks: 18%
- Review response rate: ↑14%
- Performance: <500ms load time

Follow-up:
- Add tooltip for "profile view impact" metric (next sprint)
- Consider similar widget for Capterra and Software Advice (backlog)
```

## Example 5: Failed Validation → Iterate

**User:** "Build AI-powered vendor lead quality scoring for Capterra"

### Phase 1: Discovery + Design + Implementation

*(Abbreviated—assume trio analyzed, designed, and implemented the feature)*

**Built:** AI model that scores lead quality (0-100) based on: form fields, time-on-site, pages visited, PPC keyword. Displayed to vendors in their dashboard.

### Phase 2: Validation

**Skill Orchestration:**
```
Spawn in parallel:
  - Agent 1: `performance-analysis` - Model latency and cost
  - Agent 2: `cost-optimize` - Cost at scale (5.1M visits/month)
  - Agent 3: A/B test with vendors (inline)
```

**Validation results:**
- Performance: Model latency 45ms, acceptable
- Cost: $0.08/lead scored, $12K/month at scale—acceptable
- **A/B test: Vendors confused by scoring (don't know how to use it), lead-to-sale conversion unchanged, vendor NPS ↓3 points**

**Trio analyzes failure:**

**Disagreement:**
- Designer: "The number (0-100) is meaningless to vendors—they don't know what to do with a '67' lead"
- Developer: "The model works—accuracy is 78% vs 64% baseline"
- PM: "Vendors don't want a score; they want 'call this one first' vs 'call this one later'"

**Recommendation: Pivot, don't iterate.**
Model is accurate, but presentation is wrong. Vendors don't want a score—they want **priority tiers** ("Hot leads", "Warm leads", "Cold leads") with actionable guidance.

### Phase 3: Iterate—Redesign

**Skill Orchestration:**
```
Invoke: dashboard (redesign)
Task: "Redesign lead quality scoring as priority tiers:
  - 3 tiers: 🔥 Hot (score 80-100), 💡 Warm (50-79), ❄️ Cold (0-49)
  - Each tier with guidance: 'Call within 1 hour', 'Call within 24 hours', 'Email first'
  - Dashboard: Sort leads by tier, show tier distribution chart
  - Remove the numeric score—vendors don't need to see it"
```

**Redesign complete:** Priority tiers with icons and guidance

### Phase 4: Re-validate

**A/B test (re-run for 2 weeks):**
- Vendor understanding: 89% of vendors understood tiers (vs 45% for score)
- Usage: 67% of vendors changed call order based on tiers
- **Lead-to-sale conversion: ↑12% (vs unchanged in original test)**
- Vendor NPS: ↑5 points (vs ↓3 in original test)

**Trio validates:**

**POV Designer:** "Tier presentation works—vendors understand actionable guidance"

**POV Developer:** "Model unchanged (still accurate), just new presentation layer"

**POV Product Manager:** "Win: ↑12% conversion because vendors prioritize correctly. Ship to 100%."

**Output:**
```
AI lead quality scoring: SHIPPED (after pivot to tier presentation)

Original approach: FAILED
- Score (0-100) confused vendors
- No behavior change, NPS ↓3

Pivot to tiers: SUCCESS
- 🔥💡❄️ Hot/Warm/Cold with guidance
- ↑12% lead-to-sale conversion
- Vendor NPS ↑5

Lesson: Accurate model ≠ useful feature. Presentation matters as much as accuracy.
```

## Key Patterns Demonstrated

1. **Simple discovery** → Competitive analysis informs recommendation
2. **Parallel execution** → Design + Implementation run simultaneously with coordinated contract
3. **Parallel exploration** → Three POVs each test their approach, synthesize findings
4. **Sequential pipeline** → Discovery → Design → Implementation → Validation in stages
5. **Failed validation** → Pivot based on findings, re-validate, succeed

These patterns apply across all brands and trio sides. The orchestration system adapts the skill selection, but the coordination patterns remain consistent.
